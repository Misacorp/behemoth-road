# @behemoth-road/core

The game rules: pure, headless and seeded. No UI, network or storage code. Every function takes a state (and an input) and returns a new state; the same seed and inputs always give the same result. The core knows hex coordinates only, never screen positions.

## Server and client

- **`GameState`** (server only) is **`GameStateView`** plus the `seed`. `toPlayerView(state)` strips the seed, field by field. Every known tile carries its `terrain` id, so a view can draw the map and run every rule a client needs (`move`, `planPath`, `reachablePlaces`, `legalMoves`, `entryInto`, `visibilityAt`, `predictCreature`), with the same results as on the server. `terrainOf(state, hex)` reads known terrain and generates only when the state has a seed; on a view an unknown hex has no terrain and cannot be entered.
- Server only (need the seed): `createGame`, `nextDay`, `chooseCreatureStep`, `rollCharacters`, `characterOffers`, `addCharacter`, `replaceCharacter`, `loadGame`.
- **Storage:** a game records `contentVersion` (`CONTENT_VERSION`). `loadGame(json)` refuses a state with an unknown version (`UnknownContentVersionError`) or without its seed. `nextDay` prunes lost tiles more than `lostTileRings` beyond the window, except under a character.

## Features, items and actions (Milestone 3)

- **Features** (`FEATURE_TYPES`: resource nodes, tomb sites in two tiers, traps) are generated on the server, sparsely and by terrain tags, as hexes come into view. They are stored in `features` by hex key as `{ type, revealed, left }`. A player view holds only revealed ones, plus `glints` (hexes a scout has sensed) and the team `inventory`.
- **Entering a hex** (`move`, `moveAlong`) reveals its feature for everyone. A hidden trap ends a non-scout's day (`trapped`), and a scout senses hidden features within `senseRadius`. Results carry `events` (`reveal`, `sense`, `trap`, `gather`, `craft`, `find`, `site-failed`). `moveAlong` checks the whole path first, then stops at a trap (`stopped: { step, reason: 'trap' }`).
- **Actions:** `checkAction(view, id, action)` says what an action costs (actions, materials, chance) or why it is refused, and `actionsHere` lists them all for the interface. `act(state, id, action)` applies one on the server: `{ kind: 'gather' }`, `{ kind: 'craft', recipe }` or `{ kind: 'work-site' }` (a seeded roll). Roles count by their tags (`reveal`, `gather`, `craft`, `sites`).
- **Items** (`ITEMS`, `RECIPES`, `MATERIALS`) belong to the team. An item's `movement` lets everyone onto matching terrain through `entryInto`, whose `via` is the item's id (the grappling hook over a cliff).
- **Storage:** content version 3. `loadGame` migrates a version-2 game (`migrateGame`): its map and characters stay, and hexes in view get their features.

## API

- **Characters:** a character has an `id`, `userId`, `name`, `trait`, `quirk` (null for the plain one), `role`, `lookSeed` (public, picks the figure's look; rolled with the offer, so the preview and the map agree), `joinedDay`, `at`, `actionsLeft` and `status`. `characterOffers(state, userId)` gives two or three rolled characters plus the plain one, seeded by the game, the user and their attempt, so a reload shows the same list (`rollCharacters(seed, userId, attempt)` underneath). `addCharacter(state, { userId, offer, role })` adds the chosen one (by index), riding the creature, one per user, up to `playerCap` active characters. `replaceCharacter` does the same only when the user's character is lost; the lost one stays. Refusals: `invalid-user`, `unknown-role`, `invalid-offer`, `has-character`, `no-character`, `not-lost`, `cap-reached`. `characterOf(state, userId)` is the user's newest character.
- **Start and advance:** `createGame(seed, { characterIds, config, heading, start })` returns day 1; `characterIds` makes plain test characters, all riding the creature. `nextDay(state)` is the day tick: the creature steps, the window and fog update, riders move with it, anyone the creature stepped onto is now riding it (no cost), characters left outside after the grace days are lost, actions reset.
- **Places:** a character's `at` is `{ kind: 'hex', hex }` or `{ kind: 'creature' }` (riding). The creature's seven footprint hexes are one place: any of them, given as a target, means the creature (`placeAt`, `toPlace`). Helpers: `ON_CREATURE`, `onHex`, `placeKey`, `placeEquals`, `placeHex` (where to draw a place), `placeNeighbours`, `creatureEdge` (the hexes beside the footprint).
- **Act:** `move(state, characterId, to)` takes a hex or a place and returns `{ ok: true, state }` or `{ ok: false, reason }` (`invalid-hex`, `unknown-character`, `character-lost`, `not-adjacent`, `unreachable`, `impassable`, `not-enough-actions`). Boarding from a hex beside the footprint and stepping off onto one each cost a normal step. `reachablePlaces(state, id)` lists every place in reach with the actions left (the creature included), with the cheapest cost. `planPath(state, id, to)` returns the cheapest path as steps (`{ place, cost, via? }`), crossing the creature when that is cheaper, or a refusal (also `no-path`). `moveAlong(state, id, steps, places or hexes)` walks it all or nothing (a refusal names the failed `step`). `legalMoves` lists one-step places. `entryInto(state, hex)` is the one rule for entering a hex: its cost and an optional `via` tag (gear, later), or null; footprint hexes are never entered as hexes.
- **Read:** `terrainAt(seed, hex)` (from seeded noise fields: regions, river and ridge ribbons), `visibilityAt(state, hex)` (`hidden` | `seen` | `lost`), `isReachable`, `windowHexes`, `isInWindow`, `creatureHexes`, `isCreatureHex`, `predictCreature(state)` (the possible next centres with chances), `findCharacter`.
- **Hex maths** (axial, flat-top; directions `n`, `ne`, `se`, `s`, `sw`, `nw`): `hex`, `hexKey`, `neighbour`, `neighbours`, `hexDistance`, `isAdjacent`, `isValidHex`, `hexesInRange`, `hexRing`, `rotate`.
- **Randomness:** a game `Seed` is four 32-bit words (`newSeed()` on the server; `toSeed(n)` for tests); `artSeed` is a separate public number for drawing (`newArtSeed()`). `hashToUnit(seed, ...ints)` for values tied to a place or day, `createRng(seed)` for local sequences, `pickWeighted`.
- **Data:** in `src/content/`: `TERRAIN_TYPES` and `TERRAIN_GENERATION` (the layout rules), `ROLES`, `TRAITS`, `QUIRKS` (each with an `icon` key; a quirk `helps` and `hinders`), name parts, and `CONTENT_VERSION`; `noiseAt` for the fields, and `DEFAULT_CONFIG` / `resolveConfig(overrides)`: every tuning number in one place (`src/config.ts`). A game stores its resolved config in its state.

`GameState` and `GameStateView` are plain JSON.
